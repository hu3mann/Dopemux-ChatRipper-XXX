## Notes
E1. Anthropic's embeddings guide says it has no embedding model and names Voyage AI (by MongoDB) as one provider. It also says to "assess a variety of embeddings vendors". Recommended Voyage models: voyage-4-large (quality), voyage-4 (balanced), voyage-4-lite (cost), voyage-code-4 (code); voyage-4-nano is open-weight (Apache 2.0, run yourself).
Design impact: Assume embeddings come from a separately chosen provider or local model, never from Anthropic.

E2. (a) The Messages create reference has no `seed` parameter. It also does not list `temperature` or `top_p` on the part read; the migration guides cover them. (b) Sonnet 5.5 returns 400 for non-default `temperature`/`top_p`/`top_k`; Opus 5.5 rejects any non-default value (guide: "Omit ... or leave them at their defaults"). (c) Forced `tool_choice` any/tool returns 400 on both models, also on token counting; use `auto` plus `strict: true` or `output_config.format`. I found no thinking-on exception. (d) Thinking runs adaptively by default on both. Opus 5.5 `disabled` is a 400; Sonnet 5.5 `disabled` is a 400 and `between_tools` turns it off. Thinking tokens count toward `max_tokens`.
Design impact: Do not rely on seed, temperature or forced tool_choice for Anthropic determinism; use structured outputs and size `max_tokens` for thinking plus answer.

E3. Structured output exists on all four but with different shapes. vLLM: `response_format` json_schema, supported by default. Ollama: native `format` field accepts a JSON schema, and it says `response_format` works via OpenAI-compat with no further detail; the cloud does not support it. llama.cpp server: `response_format` with `schema` directly inside it, as `json_object` or `json_schema`, on `/v1/chat/completions` (its doc example has a typo). LM Studio: `response_format` json_schema; "Not all models are capable ... particularly LLMs below 7B". vLLM docs state no reproducibility by default and only on the same hardware/version; batch size is not named, but batch invariance is offered as a fix. Ollama official docs only say "Set temperature to 0 for more consistent results"; the non-reproducibility claim for Ollama rests on blogs, so it is NOT_FOUND in vendor docs. llama.cpp and LM Studio reproducibility were not checked.
Design impact: Treat schema-constrained output as a per-backend capability probe, validate every output against the schema, and treat seed as best-effort only.

E4. sqlite.org section 11 of the WAL page describes a data race that can corrupt a WAL-mode database when two or more connections write or checkpoint at the same instant. Affected: 3.7.0 to 3.51.2. Fixed in 3.51.3 (2026-03-13), with backports in 3.44.6 and 3.50.7. Found 2026-03-03. Maintainers say "this is not an emergency". A reproducer without the test hook was reported 2026-08-24.
Design impact: Require SQLite >= 3.51.3 (or 3.50.7 / 3.44.6) when WAL mode has multiple connections; record the runtime sqlite_version and warn when older.

E5. The Presidio README says "Presidio has moved to a new home!" and the repo is now under the data-privacy-stack org. The transition doc says it is now an independent, community-governed project with a Technical Steering Committee, still MIT; Docker images moved to ghcr.io/data-privacy-stack. The doc does not mention V1 or V2. "Migrating from V1 to V2" appears only as an install-guide item linking docs/presidio_V2.md; I did not read that file. OpenAI Privacy Filter does exist: an open-weight PII detect/redact model that runs locally (about 1.5B total, 50M active parameters per search summaries; model card at arxiv 2608.18274). Release date about April 2026 is from a search summary only.
Design impact: Say "community-governed under the Data Privacy Stack org" without implying a V1-to-V2 migration is part of that move; treat Privacy Filter as an optional local model to evaluate, not a guaranteed 99.5% filter.

E6. RFC 9457 abstract: "This document obsoletes RFC 7807." Appendix D lists the changes (new problem-type registry, multiple-problem guidance, non-dereferenceable type URI guidance). The fetched rendering omitted the "Obsoletes:" header line, so the abstract is the quote.
Design impact: Cite RFC 9457 as the current Problem Details standard; the media type application/problem+json is unchanged.

E7. In Click's source, `UsageError.exit_code` is 2, overriding `ClickException`'s default of 1. Typer is built on Click, but I did not fetch Typer docs, so Typer behaviour is inferred. Errors raised as other ClickException subclasses exit 1 unless they set their own code. Which statuses the design's CLI should use for non-usage errors is not covered here.
Design impact: Assume exit 2 for CLI usage errors (bad flags/arguments) and 1 for other ClickException; do not reuse 2 for domain errors.

E8. uv supports path sources, including `editable = true`, pointing at a project directory. For another workspace, uv also supports `foo = { workspace = "../other-workspace" }`; the path "must point to the external workspace root" and uv picks the member matching the dependency name. uv notes that for members with conflicting requirements or separate environments, path dependencies "are often preferable", but then `uv run --package` is unavailable. I did not find text on a path source that points at a member directory of another workspace. `workspace = true` is for members of the same workspace and is always editable.
Design impact: A path source to the other repo's member directory is valid but is a plain path dependency (the other workspace's lock and sources are not applied); use `workspace = "<root>"` if member-aware resolution is wanted, and expect separate requires-python and lockfiles.

E9. The README says only "pre-v1"; the vec0 doc page strongly implies exact scan ("wasteful to perform a brute-force search over all documents", partition keys to narrow scans) but never says "brute-force" about default KNN outright. Issue #25 (open since 2024-06-21; no linked PR or release) says v0.1.0 was "brute-force search only" and lists IVF, HNSW and DiskANN as candidates. The owner said in Oct 2024 to start with IVF+kmeans and add DiskANN later, then posted no update. The repo tree has sqlite-vec-diskann.c and sqlite-vec-ivf.c files, but nothing documents or releases them. Latest release is v0.1.9 (2026-03-31), not a pre-release flag, but the project is pre-v1.
Design impact: Assume exact O(N) scan per query in vec0 and a pre-v1 API; size corpora accordingly and do not plan on an ANN index shipping.
